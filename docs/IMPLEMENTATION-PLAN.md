## 2. Какие вопросы закрылись

- **Поиск использует отдельную БД.** Место и предложения хранятся раздельно.
- **Одно событие — `CatalogChanged`.** Названия `PlaceChanged`/`OfferChanged` в старом тексте модели поиска считаем устаревшими относительно принятого контракта.
- **Топик и ключ определены:** `catalog.search.events`, ключ — UUID места.
- **Расписание структурированное:** группы одинаковых интервалов по дням, местное время, конец `24:00` допустим.
- **Версии независимы:** изменение категории меняет снимок места, изменение расписания — снимок предложения. Повтор сообщения сохраняет версии и ID.
- **Срок действует включительно:** истечение после местной полуночи следующего дня. Проверка даты в выдаче обязательна независимо от фонового обновления статуса.
- **Публикация запускается подтверждённым событием Submission:** `SubmissionStatusChanged → APPROVED`, а не входящим решением модератора.
- **Конфликт CHANGE уже поддержан:** `OfferPublicationConflicted`, причина `CATALOG_VERSION_CONFLICT`, возврат к проверке новой версии.

## 3. Этапы реализации

### A. События и версии

1. Новая миграция, без изменения V1/V2: отдельные `event_revision` и последний отправленный снимок места/предложения.
2. Формирование полных снимков строго по принятому контракту. Закрытые источники, условия, вложения и ссылки на заявки в поиск не передавать.
3. Сравнение JSONB: одинаковые числа с разным scale не создают ложные изменения.
4. Блокировка места, изменение нужных версий и вставка готового outbox в одной транзакции.
5. Переименование категории публикует отдельное событие для каждого места. Повторное сохранение прежних данных не публикует события.
6. При обновлении существующей БД первоначальные снимки создаются отдельным возобновляемым обработчиком. Это начальная выгрузка, не протокол восстановления потерянного индекса.

### B. Актуальность и полная карточка

1. Фоновая обработка только ACTIVE со сроком раньше текущей местной даты.
2. Изменение статуса, версии строки и поискового снимка вместе с outbox.
3. Публичный GET полной карточки места; выдача только ACTIVE внутри общего срока.
4. Расписание показывается целиком; решение о фильтре «действует сейчас» не подменяется скрытым фильтром.
5. Закрытый `source.note`, подтверждения и служебные версии не попадают в публичный ответ. Внутренние маршруты Submission сохраняются.

### C. Доставка

1. Outbox выбирается по порядку записи. Более новое событие одного места не обходит старое, даже при двух отправителях.
2. Отметка об отправке ставится после подтверждения Kafka. Сбой до commit допускает повтор с тем же ID и телом.
3. Workflow сохраняет действующий обычный JSON.
4. Search использует отдельную сериализацию JSON Schema с ID схемы; выбран совместимый с Confluent Registry адаптер. Это конкретизация ещё не выбранной командой инфраструктуры.
5. Schema Registry: `TopicNameStrategy`, subject `catalog.search.events-value`, `BACKWARD_TRANSITIVE`; регистрация отдельным скриптом, автоматическая регистрация приложением отключена.

### D. Приём заявок и недостающие метаданные

1. Сохранять `SubmissionSubmitted`/`SubmissionVersionCreated` и подтверждённые состояния из `submission.events.v1`.
2. Проверять ключ, тип, автора сервиса, версию схемы, хеш снимка, ID события; повтор с изменённым содержимым отклонять.
3. Не использовать более старое состояние после нового; хранить снимки независимо от порядка доставки.
4. Новый отдельный контракт `catalog.publication.metadata.v1` передаёт тип, сохранённый часовой пояс и исходную версию места для конкретной неизменяемой версии заявки.
5. Обработчик ждёт снимок, метаданные и APPROVED одной версии. Без любого элемента данные остаются в БД, публикации нет.
6. Публикация и её результат атомарны. Конфликт изменения откатывает все изменения карточки и формирует согласованный ответ Submission.
7. Некорректные метаданные или истёкшая к моменту публикации скидка фиксируются как BLOCKED. Общего события ошибки публикации у Submission пока нет, успешный результат не имитируется.

### E. Проверка и ревью

- Сохранить старые тесты внутреннего API и публикации.
- Проверить V1→V6 на существующих данных и развёртывание пустой БД.
- Проверить снимки, расписание, версии категории/места/предложения, подавление повторов.
- Проверить местную полночь, идемпотентность и конкурентное истечение.
- Проверить отсутствие закрытых полей и фильтрацию до фоновой обработки.
- Проверить порядок двух отправителей и повтор после подтверждения Kafka при потере commit БД.
- Проверить реальный Kafka; отдельно сериализатор с тестовым Schema Registry client.
- Проверить пропущенные метаданные, переупорядоченные события, конфликт версий и недопустимые входы.
- Два независимых ревью: события/БД и интеграция/публичная выдача. Исправления проходят повторные целевые проверки.

## 4. Что нужно связать при интеграции в dev

Это реализация согласованного с владельцем подхода: расхождения не блокируют разработку, но оформляются явно.

| Участник | Что потребуется |
|---|---|
| Submission | Публиковать `SubmissionPublicationMetadata` для проверенной версии; сохранять исходную версию места при подготовке CHANGE; не вычислять её заново перед отправкой |
| Search | Реализовать обработчик `CatalogChanged`, чтение Registry, независимые версии и удаление неактивных предложений |
| Инфраструктура | Брокер, Registry, создание топиков, одинаковый subject/schema, права Kafka, маршрутизация только публичного API наружу |
| Команда | Решить общий результат публикации для ошибок кроме конфликта CHANGE; протокол полного восстановления поисковой БД |

Изменения чужих сервисов и общей документации в эту ветку не входят. Новый metadata-контракт и конкретный Registry-адаптер нельзя выдавать за уже внедрённые коллегами. Работоспособность каталога проверяется отдельно от готовности всей платформы.

## 5. Уточнения по ревью

Добавлены независимая задержка неудачной доставки, карантин некорректных Kafka-записей, поддержка неполного источника при наличии PROOF и прикладная проверка сложных ограничений расписания. Тесты отдельно проверяют, что ошибка поиска не останавливает подтверждения Submission, а неверный снимок не блокирует другие заявки.
