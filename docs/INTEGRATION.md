# Интеграция каталога

## Текущее состояние

Catalog реализует свою сторону публикации, полной карточки и синхронизации поиска. Основа: `submission 5cc3d1c`, `docs 4f4dd1f`, контракт `CatalogChanged 1b5fa89`. Код коллег не изменён.

Два решения пока являются предложением для общей интеграции:

- дополнительное событие `SubmissionPublicationMetadata`;
- Confluent-совместимый Schema Registry, `TopicNameStrategy` и subject `catalog.search.events-value`.

Принятый контракт уже требует Registry, но не выбирает его реализацию и subject. Содержимое `CatalogChanged` сохранено. Поисковый consumer в репозитории Search ещё не реализован.

## 1. Входящие события

`submission.events.v1` остаётся действующим контрактом Льва. Ключ — строковый `submissionId`, значение — обычный JSON.

Каталог сохраняет версии из `SubmissionSubmitted`/`SubmissionVersionCreated` и статус из `SubmissionStatusChanged`. Хеш снимка проверяется по нормализации из `Submission.domain.PayloadJson` (`5cc3d1c`), без зависимости сборки от чужого репозитория. Снимок неизменяем; повтор с тем же ID и другим содержимым отклоняется.

Публикация возможна только при последнем подтверждённом `APPROVED`. Входящее сообщение модератора `SubmissionApproved` не принимается за разрешение публикации. Порядок состояний задаётся `aggregateSequence`; поздний старый статус не отменяет новый. Если снимок пришёл позже статуса, он сохраняется и затем используется, не откатывая состояние.

### Дополнительный контракт метаданных

Топик: `catalog.publication.metadata.v1`. Ключ: `submissionId`. JSON Schema: [submission-publication-metadata.schema.json](../src/main/resources/contracts/submission-publication-metadata.schema.json).

```json
{
  "eventId": "0e7f4302-a086-48c6-9185-ad9bab03d0a9",
  "eventType": "SubmissionPublicationMetadata",
  "schemaVersion": 1,
  "producer": "submission",
  "occurredAt": "2026-11-19T12:00:00Z",
  "correlationId": "publication-example",
  "data": {
    "submissionId": "cb6f9369-5ced-4e6f-98c2-e937b60c274d",
    "versionId": "05ef72ca-09f3-49e7-a2db-58ec3a4c769c",
    "versionNo": 1,
    "type": "NEW_PLACE",
    "resolvedTimezone": "Europe/Moscow",
    "basePlaceRowVersion": null
  }
}
```

Это дополнение не меняет существующую строгую схему `submission.events.v1`. Его издатель должен взять тип и часовой пояс из сохранённой проверенной версии. Для изменения места `basePlaceRowVersion` фиксируется при подготовке версии, как версия скидки; подставлять текущую версию непосредственно перед публикацией нельзя.

Снимок, метаданные и одобрение связываются по тройке `submissionId/versionId/versionNo`. Метаданные могут прийти до или после одобрения. Отсутствие любой части оставляет заявку ожидающей в БД. Новая схема не означает, что Submission уже публикует это сообщение: этот участок надо добавить там при интеграции.

### Результат

- Успех: `OfferPublished` в `submission.workflow.v1`, с ID созданных/изменённых предложений.
- Устаревшее изменение скидки/места: `OfferPublicationConflicted` с `CATALOG_VERSION_CONFLICT`. Изменения карточки откатываются до сохранения ответа о конфликте.
- `expectedRowVersion` — версия строки заявки из подтверждённого APPROVED, не версия скидки.
- Другие бизнес-ошибки сохраняются в `catalog_submission_state.publication_outcome=BLOCKED` и `publication_error`. Общего результата ошибки у Submission пока нет. Каталог не отправляет ложный успех или несогласованный статус.

Для исправления заблокированного содержания нужна новая проверенная версия. Для восстановления после инфраструктурной ошибки достаточно восстановить зависимость: незафиксированная обработка повторится. Удалять inbox или переписывать уже проверенный снимок нельзя.

## 2. Поисковые события

[JSON Schema](../src/main/resources/contracts/catalog-changed.schema.json) соответствует принятой структуре `CatalogChanged`.

- Топик `catalog.search.events`, ключ — `placeId`.
- Версии `event_revision` независимы от блокировочных `row_version`.
- Место и предложения сравниваются с предыдущим JSONB-снимком. Нет изменения снимка — нет новой версии и события.
- `CatalogCategories.save` переименовывает категорию и создаёт события мест одной транзакцией. Низкоуровневый `CatalogRepository.saveCategory` не является прикладным API изменения категорий; прямой SQL обходит публикацию событий.
- Снимки содержат все поля, включая nullable-значения и полный набор интервалов. Неактивное предложение передаётся полным снимком со статусом, а не пустым удалением.
- В тело не добавляется `schemaVersion`. Сериализатор Confluent передаёт ID зарегистрированной схемы в транспортном заголовке сообщения.

Первичная выгрузка после V3 создаёт события только для мест, у которых ещё нет снимка. Она повторяема и работает пачками. Полное восстановление потерянной поисковой БД требует отдельного протокола snapshot/replay и достаточного retention Kafka; эту функцию начальная выгрузка не заменяет.

### Регистрация схемы

Нужны `curl`, `jq` и доступ к Registry. Для локального окружения:

```bash
CATALOG_SCHEMA_REGISTRY_URL=http://localhost:18085 ./scripts/register-search-schema.sh
```

Скрипт устанавливает `BACKWARD_TRANSITIVE` для subject и регистрирует JSON Schema с `normalize=true`. В сериализаторе включено `normalize.schemas=true`: форматирование и порядок свойств схемы не должны менять её идентификатор. Несовместимую новую версию Registry отклонит. На рабочем окружении регистрацию выполняет ответственный за схемы с настроенной аутентификацией Registry, сначала развёртываются потребители. Приложение работает с `auto.register.schemas=false` и не меняет настройки Registry.

## 3. Доставка и повторные попытки

Данные, версии и outbox сохраняются атомарно. Отправитель удерживает блокировку самого раннего неопубликованного события пары topic/key до подтверждения брокера и commit БД. Другой отправитель не может пропустить его и отправить следующее событие того же места.

Сбой после подтверждения Kafka, но до commit БД приводит к повтору с неизменным телом и `eventId`. Гарантия — at least once. Потребителям необходима собственная дедупликация/проверка версий.

Отправитель продолжает проход после ошибки и запоминает позицию обхода между пачками. Медленно отвечающие неисправные потоки не должны постоянно оттеснять исправные. Позиция обхода — временная подсказка, а порядок и подтверждения сохраняются в БД. Неудачная отправка откладывается на пять секунд; последующие события того же ключа ждут, независимые ключи и топики могут продолжать работу. `delivery_failures` позволяет обнаруживать повторные ошибки. Отключённый транспорт не помечает сообщения доставленными.

Некорректное входящее событие сохраняется в приватной таблице `catalog_inbox_quarantine` вместе с topic/partition/offset, исходным ключом и телом. Kafka подтверждается только после сохранения карантина; при сбое БД запись повторяется. Это позволяет следующему корректному сообщению продолжить обработку. Транзитные ошибки инфраструктуры повторяются без пропуска. Карантин содержит закрытые данные заявки: доступ только для сопровождения, без публикации в API и логах. После исправления причины сообщение повторно публикуют в исходный топик с сохранённым eventId; не правят снимки напрямую.

## 4. Публичная карточка

`GET /api/v1/catalog/places/{id}` — отдельный публичный контракт, [OpenAPI](../src/main/resources/static/openapi.json). Место без действующих публичных предложений возвращает 404.

Показываются только ACTIVE в общем сроке по часовому поясу места. `validUntil` включителен; `validFrom` исключает будущие предложения. Расписание возвращается, но не скрывает скидку вне её часов: фильтр «действует сейчас» отдельно не согласован.

В ответе есть условия, категория, даты, расписание и тип/ссылка источника. Нет `source.note`, вложений-подтверждений, ссылок на заявки и внутренних версий. Старый `/catalog/v1` сохраняет расширенные ответы для Submission и должен оставаться во внутренней сети. При публикации через Gateway разрешать только `/api/v1/catalog/**`, не весь порт сервиса.

## 5. Настройки

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `CATALOG_SUBMISSION_ENABLED` | false | Kafka consumer и обработчик одобренных версий |
| `CATALOG_SUBMISSION_GROUP_ID` | catalog-publication-v1 | Группа consumer |
| `CATALOG_WORKFLOW_DELIVERY_ENABLED` | false | Отправка результатов в Submission |
| `CATALOG_SEARCH_DELIVERY_ENABLED` | false | Отправка в Search через Registry |
| `CATALOG_KAFKA_BOOTSTRAP_SERVERS` | localhost:9092 | Адрес брокера; задаётся для конкретного окружения |
| `CATALOG_SCHEMA_REGISTRY_URL` | пусто | Обязателен при включённой поисковой отправке |
| `CATALOG_EXPIRATION_ENABLED` | true | Перевод истёкших ACTIVE в EXPIRED |
| `CATALOG_EXPIRATION_DELAY_MS` | 60000 | Период проверки |
| `CATALOG_BOOTSTRAP_ENABLED` | true | Первоначальные события для данных до V3 |

Транспортные обработчики выключены до настройки брокера, Registry и прав. Это не отключает формирование durable outbox. Секреты не входят в репозиторий; Kafka TLS/SASL и Registry-аутентификация задаются стандартными `spring.kafka.*` свойствами. Право записи в metadata/events принадлежит только доверенному Submission. Поле `producer` само по себе не аутентифицирует отправителя.

## 6. Методика проверки

Как в Submission: Java 25, отдельные прикладные сервисы, SQL и транзакции, реальные PostgreSQL/Kafka для интеграционных проверок, сохранение идентификаторов при повторе, отсутствие зависимости сборки от репозиториев коллег.

Тесты проверяют БД и публичный HTTP, а не только вызовы mock-объектов. Registry-сериализация проверяется официальным сериализатором с `MockSchemaRegistryClient`; это не проверка развёрнутого Registry или совместимости с ещё отсутствующим consumer Search. Совместный запуск всей платформы отдельно не заявляется.

Частично заполненный `source` при наличии подходящего PROOF не считается источником: при сборке карточки он опускается, а исходный снимок в inbox сохраняется без изменений. Диапазон процентов при авторинге остаётся 1–100, как в Submission и DATA-MODEL; поисковая схема допускает более широкий диапазон >0–100.

JSON Schema проверяет структуру и числовые границы. Дополнительная проверка сериализатора контролирует уникальность дней/предложений, порядок и пересечение интервалов, суммарный предел 28 развёрнутых интервалов, порядок дат и существование часового пояса.

Переименование категории обрабатывает все связанные места атомарно; стоимость пропорциональна их числу. Изменение только порядка/активности категории не сканирует места. Для больших массовых операций понадобится отдельное решение, сохраняющее снимки и outbox в согласованной транзакции.

Настройка нормализации и транспортного формата сверена с [документацией Confluent](https://docs.confluent.io/platform/current/schema-registry/fundamentals/serdes-develop/index.html#schema-normalization) и [описанием JSON Schema serializer](https://docs.confluent.io/platform/current/schema-registry/fundamentals/serdes-develop/serdes-json.html).
