# Catalog Service

Опубликованные места и скидки Student Discounts. Java 25, Spring Boot 4.1.2, PostgreSQL 17 + PostGIS 3.5, Spring JDBC, Flyway, Kafka.

## Что реализовано

- Модель места, скидки, категории, расписания и подтверждений; ограничения данных и миграции.
- Публикация проверенного снимка, защита от повторов и конфликтующих изменений места/скидки.
- Приём событий Submission в durable inbox. Публикация после подтверждённого APPROVED, снимка и метаданных одной версии.
- `OfferPublished` и `OfferPublicationConflicted` по действующему контракту Submission.
- `CatalogChanged`: независимые версии снимков, группировка расписания, изменения категории, статуса и данных.
- Outbox с подтверждением Kafka, порядком внутри ключа, повтором без смены ID и задержкой после сбоя.
- JSON Schema сериализация событий поиска через Confluent-совместимый Registry.
- Автоматическое истечение скидок после окончания местного дня.
- Отдельный публичный API полной карточки и прежний внутренний API для Submission.

## Границы интеграции

Реализация опирается на `submission dev 5cc3d1c` и принятые документы `docs dev 4f4dd1f`. Search пока содержит каркас приложения.

**Новое событие `SubmissionPublicationMetadata` ещё нужно добавить на стороне Submission.** Действующие события не передают сохранённый часовой пояс версии и исходную версию места. Каталог уже принимает отдельный metadata-контракт и ждёт недостающие данные, не публикуя непроверенную карточку. Код коллег не изменён.

Confluent-совместимый Registry и subject `catalog.search.events-value` выбраны здесь как конкретный вариант для последующей интеграции. Поля `CatalogChanged` соответствуют принятому контракту. Общий Registry и consumer Search ещё нужно подключить.

Модель заявок, их черновики и проверку обязательных полей повторно не реализуем: они принадлежат Submission. Модерация, проверка файлов и членство организаций остаются у своих владельцев. `organization_id` зарезервирован, не заполняется.

## Сборка и тесты

Нужны JDK 25 и Docker. Используются настоящие PostgreSQL/PostGIS и Kafka через Testcontainers; нет H2 и пропуска контейнерных тестов.

```bash
export JAVA_HOME=/opt/homebrew/opt/openjdk@25/libexec/openjdk.jdk/Contents/Home
./gradlew build
```

На другом компьютере укажите путь к своему JDK 25. Для отдельного профиля Colima:

```bash
colima start --profile sd-model --activate=false
export DOCKER_HOST="unix://$HOME/.colima/sd-model/docker.sock"
export TESTCONTAINERS_DOCKER_SOCKET_OVERRIDE=/var/run/docker.sock
./gradlew build
```

На ARM для `postgis/postgis:17-3.5` нужна эмуляция amd64. Gradle Wrapper фиксирует версию 9.1.0. Новый сериализатор загружается из официального Maven-репозитория Confluent, ограниченного группой `io.confluent`.

Отчёт: `build/reports/tests/test/index.html`. Тесты проверяют публикацию, реальные SQL-ограничения, обновление существующей БД, HTTP, события, версии, повторы, конфликты, местную полночь, конкурентных отправителей и Kafka. Registry проверяется официальным сериализатором с тестовым клиентом, не внешним сервером.

## Локальный запуск

```bash
docker compose up -d --wait
./gradlew bootRun --args='--spring.profiles.active=local'
```

Приложение слушает `127.0.0.1:8084`, PostgreSQL — `127.0.0.1:5436`. Порт 8084 совпадает с upstream каталога в Kong (`gateway/kong.yml`), 5436 выбран, чтобы не пересекаться с базами auth (5432), submission (5433), moderation (5434), media и search (5435).

Ошибки сервиса, включая неизвестный путь, возвращаются в формате `application/problem+json`: `type`, `status`, `code` и `correlationId` из заголовка `X-Correlation-ID`.

Kong обращается к сервисам через `host.docker.internal`. На macOS с Colima или Docker Desktop это доходит до `127.0.0.1`. На Linux `host-gateway` указывает на адрес моста, поэтому нужен `CATALOG_BIND_ADDRESS=0.0.0.0`. По умолчанию каталог остаётся на loopback: внутренние маршруты `/catalog/v1` отдают приватные поля без сервисной аутентификации, их нельзя открывать в сеть. Локальные credentials есть только в Compose и локальном профиле. Вне локального профиля нужны `CATALOG_DB_URL`, `CATALOG_DB_USER`, `CATALOG_DB_PASSWORD`.

При таком запуске доступны чтение и обработка сроков. Kafka consumer/отправители выключены, outbox сохраняется. Для включения нужны брокер, топики, metadata-издатель и Registry; флаги и порядок приведены в [инструкции интеграции](docs/INTEGRATION.md).

База изначально пустая. Прикладные изменения справочника выполняются через `CatalogCategories.save`, который обновляет поисковые снимки связанных мест. Прямые SQL-изменения справочника обходят генерацию событий. Публичного административного API категорий нет.

## HTTP

| Маршрут | Доступ и содержание |
|---|---|
| `GET /api/v1/catalog/places/{id}` | Публичная карточка с доступными предложениями, без закрытых заметок и подтверждений |
| `GET /openapi.json` | Спецификация публичного API |
| `GET /catalog/v1/categories/{code}` | Внутренний: `code`, `name`, `sortOrder`, `isActive` |
| `GET /catalog/v1/places/{id}` | Внутренний: место, `location.lat/lon`, `timezone`, `rowVersion` |
| `GET /catalog/v1/offers/{id}` | Внутренний: `id`, `placeId`, `status`, `rowVersion`, полный `payload` |
| `GET /actuator/health` | Проверка состояния без закрытых подробностей |

Внутренние маршруты содержат `source.note` и ссылки на подтверждения: не публиковать их через Gateway. Submission вызывает их без bearer-токена; этот существующий контракт сохранён. Межсервисную защиту задаёт окружение, нельзя выдавать loopback-привязку за настроенную production-аутентификацию.

Публичная карточка включает только ACTIVE внутри общего срока. Место без таких предложений возвращает 404. Расписание отображается, но не применяется как фильтр «действует сейчас». Новые write-операции через публичный HTTP не добавлены.

## Данные и восстановление

V1/V2 сохранены без изменений. V3 добавляет версии поисковых снимков и порядок outbox; V4 — inbox, версии и метаданные; V5 — задержку повторной доставки; V6 — приватный карантин некорректных сообщений. Flyway применяется при запуске.

Начальная выгрузка создаёт поисковые события для мест без ранее сохранённого снимка. Она не заменяет восстановление целиком потерянного индекса: для этого команде нужно согласовать snapshot/replay и retention.

Сохраняйте PostgreSQL вместе с inbox/outbox и снимками. После сбоя подтверждённые сообщения могут прийти повторно. Не очищайте outbox, inbox и историю Flyway для обхода ошибки. Ошибка публикации не превращается в успех: `publication_outcome=BLOCKED` и код причины доступны в `catalog_submission_state`.

Полный Spring/Kafka-сценарий проверен с действующими слушателями и фоновыми обработчиками; миграции проверены как на пустой БД, так и поверх V2 с данными.
